# Templates

mirrortest lays generated files out with [inja](https://github.com/pantor/inja)
templates. The defaults are compiled into the binary; `--templates DIR`
replaces any of them with a file of your own, for example to match a house
style for file headers or section comments.

The header the `hook` stub policy needs (`mt_not_implemented.h`) is not a template: it is
plain text with nothing to restyle but the file header, which it takes from the
configuration.

A template only *places* text. Everything that needs a decision is computed by
the tool and handed over already formatted: how a signature is spelt, which
includes a type needs, what a stub's body is. That is deliberate. Overriding a
template cannot change what the tool infers, only where it puts it.

## Overriding

```console
$ mirrortest gen-impl tests/foo_test.cpp --out src/ --templates my-templates/
```

A file in `my-templates/` replaces the built-in template with the same relative
path. Everything else stays built in:

```
my-templates/
└── common/
    └── file_header.inja     replaces the built-in common/file_header.inja
```

- Only built-in names can be overridden. A `.inja` file that matches none is
  reported as a warning and ignored; it is nearly always a typo, and the
  alternative is an override that silently never takes effect. Use
  `--verbose` to list which templates were replaced.
- Templates use LF line endings. CRLF in an override is converted.
- A template that fails to parse, or uses a variable the tool does not provide,
  is an error naming the template and, where inja knows it, the line. Until it
  is fixed no template renders, so you are never left with half an override.
- A template may `{% include "common/file_header.inja" %}` any template, built
  in or overridden.

## Writing a template

Blocks (`{% ... %}`) on a line of their own leave no blank line behind
(`trim_blocks` and `lstrip_blocks` are on). Referring to a variable that is not
defined is an error, not an empty string.

**One quirk to know.** inja's `trim_blocks` removes the *spaces and tabs* after
a block tag as well as the newline that follows it (Jinja removes only the
newline). So

```jinja
mirrortest{% if source != "" %} from {{ source }}{% endif %}
```

renders as `mirrortestfrom tests/foo_test.cpp`: the space after `%}` is gone.
Keep a space that must survive inside an expression:

```jinja
mirrortest{% if source != "" %}{{ " from " }}{{ source }}{% endif %}
```

Objects in the view model iterate in sorted key order, not the order they were
built in. Anything whose order matters is therefore passed as an array.

## The templates

### `common/file_header.inja`

The first lines of every generated file.

| Variable | Type | Meaning |
|---|---|---|
| `file_header` | string | the `file_header` configuration text (a C++ comment, without a trailing newline), or `""` |
| `source` | string | the file the output was generated from, as given on the command line, or `""` |

Output: the optional `file_header`, then
`// Generated by mirrortest from <source>. Review every TODO(mt).`, ending in a
newline.

### `impl/header.inja`

One generated header (`gen-impl`). Both this template and `impl/source.inja`
start with `{% include "common/file_header.inja" %}`, so they receive its
variables too.

| Variable | Type | Meaning |
|---|---|---|
| `file_header`, `source` | string | as for `common/file_header.inja` |
| `pragma_once` | bool | `guard: "pragma-once"` in the configuration |
| `guard` | string | the include-guard macro (`ACME_FOO_H`), also set with `pragma_once` |
| `includes_begin`, `includes_end` | string | the region markers around the includes, `// <mt:begin includes>` |
| `includes` | array of string | whole `#include` lines: system headers alphabetically, then local ones |
| `sections` | array | one per namespace, in order of first appearance |

A section:

| Field | Type | Meaning |
|---|---|---|
| `open`, `close` | array of string | the `namespace x {` and `}  // namespace x` lines; empty for the global namespace |
| `blocks` | array | what the namespace holds, in order; each has a `kind` |

A block of `kind` `"forward"` has `lines` (`class B;`). One of `"class"` has
`head` (`class Foo {`), `access` (`public:`, or `""` for a struct), `begin` and
`end` (the region markers), `members` and `tail` (`};`). One of `"functions"` has
`begin`, `end` and `members`. Each member is `{notes, line}`: `notes` are whole
comment lines (`// TODO(mt): ...`), `line` the declaration, ending in `;`.

The default lays a class out with its members indented four spaces, the region
markers inside the braces, and one blank line between blocks.

### `impl/source.inja`

The stubs for one header.

| Variable | Type | Meaning |
|---|---|---|
| `file_header`, `source` | string | as above |
| `own_include` | string | `#include "acme/foo.h"`, for the header this file defines |
| `includes_begin`, `includes_end`, `includes` | | as above; the system headers the stubs need (`<stdexcept>`, `<cstdlib>`) |
| `sections` | array | one per namespace that has something to define |

A section has `open` and `close` as above, and `blocks`: each `{begin, end,
definitions}`, the region markers and an array of definitions. A definition is
`{lines}`, its lines complete and indented (`unsigned int Foo::size() const {`,
`    throw ...;`, `}`), because how a signature and a body are spelt is decided in
C++ and tested there.

### `gtest/test_file.inja`

One generated GoogleTest file (`gen-tests`). It starts with
`{% include "common/file_header.inja" %}`, so it receives that template's
variables too.

| Variable | Type | Meaning |
|---|---|---|
| `file_header`, `source` | string | as for `common/file_header.inja`; `source` is the header the tests were made from |
| `includes` | array of string | whole `#include` lines: system headers alphabetically (`<gtest/gtest.h>`, `<utility>`), then local ones (the header under test) |
| `sections` | array | one per namespace, in order of first appearance |

A section has `open` and `close` (the `namespace x {` and `}  // namespace x`
lines; empty for the global namespace), `fixtures` (an array of `{name, lines}`:
the whole fixture class, complete and indented, for the suites that have one
with `gtest.fixture`; empty otherwise) and `tests`: an array of
`{suite, name, lines}`. `lines` is the whole test, complete and indented
(`TEST(FooTest, size) {`, `    FAIL() << "...";`, `}`), because how a statement is
spelt -- the placeholder as `FAIL()` or `GTEST_SKIP()`, a statement that could
not be built as a comment, a `static_assert` -- is decided in C++ and tested
there. `suite` and `name` are for a template that wants to lay tests out
differently (a header comment per test, say).

A case that runs over a table (`gtest.parameterised`) has in its `lines` the
parameter struct, the class, the `TEST_P` and the instantiation, with blank lines
between: they are one block to the template, which puts a blank line after it
like any other test.

The default puts a blank line after the file header, none between the
includes, one around the namespace braces, one after each fixture and one between
tests; nothing inside the namespace is indented. With a fixture, `lines` begins
with `TEST_F(` instead of `TEST(`.

### `gtest/mock_file.inja`

One gmock mock header (`gen-tests` with `gtest.mocks`). It starts with
`{% include "common/file_header.inja" %}` too.

| Variable | Type | Meaning |
|---|---|---|
| `file_header`, `source` | string | as above |
| `pragma_once` | bool | `guard` is `pragma-once` |
| `guard` | string | the include guard made from the path of the header (`MOCK_SENSOR_H`); unused with `pragma_once` |
| `includes` | array of string | whole `#include` lines: `<gmock/gmock.h>`, then the interface's header |
| `open`, `close` | array of string | the `namespace x {` and `}  // namespace x` lines of the interface's namespace; empty for the global one |
| `lines` | array of string | the class, complete: its `TODO(mt)` notes as comments, `class MockSensor : public Sensor {`, one `MOCK_METHOD(...)` line each, `};` |

How a `MOCK_METHOD` is spelt -- the specifiers in the order `const`,
`ref(&)`, `noexcept`, `override`, and the parentheses around a type that has a
comma -- is decided in C++ and tested there. The default puts the guard after
the file header, a blank line after it and one around the namespace braces.

### `qtest/test_file.inja`

One generated Qt Test file (`gen-tests --framework qtest`). It starts with
`{% include "common/file_header.inja" %}`, so it receives that template's
variables too.

| Variable | Type | Meaning |
|---|---|---|
| `file_header`, `source` | string | as for `common/file_header.inja` |
| `includes` | array of string | whole `#include` lines, as for `gtest/test_file.inja` (`<QtTest>`, `<utility>`, then the header under test) |
| `sections` | array | one per namespace, in order of first appearance |
| `main` | array of string | what ends the file, outside every namespace: the entry-point macro (`QTEST_GUILESS_MAIN(acme::TestFoo)`), the comment about AUTOMOC and the `#include "tst_foo.moc"`; empty if there is no test class |

A section has `open` and `close` (the namespace lines; empty for the global
namespace) and `classes`: each `{name, head, tests}`. `head` is the whole
declaration of the test class, complete and indented (`class TestFoo : public
QObject {`, `    Q_OBJECT`, `private slots:`, one `    void size();` per test,
`};`). `tests` is an array of `{name, lines}`; `lines` is one slot's
definition, complete and indented (`void TestFoo::size() {`, `    QFAIL("...");`,
`}`).

The default puts a blank line after the file header, none between the includes,
one around the namespace braces, between the class and each slot, and before
the entry point; nothing inside a namespace is indented. A project that puts
its slots in the class body instead overrides this template and builds them from
`tests[].lines`.

With `qtest.data_driven`, a case that runs over a table is two entries of `tests`
(`name` is `<case>_data` for the first), and the class has a `void <case>_data();`
line before the slot's in `head`.
